# Git 工作树管理约定

本项目的工作树可能在 AI 开始工作前就存在用户自己的未提交改动。AI 修改源码后，Git 会继续保留这些改动；因此不能把修改后的全部差异都当成 AI 本次产生的内容，也不能让大量未提交改动长期堆积在工作树中。

## 强制流程

1. **修改前记录状态**
   - 在修改源码前查看 `git status --short`。
   - 记住或记录已有的修改文件，作为本次工作的基线。
   - 不覆盖、回退、清理或重置基线中的改动。

2. **修改后核对状态**
   - 完成源码修改后再次查看 `git status --short`。
   - 使用 `git diff --stat` 和必要的 `git diff -- <path>` 核对实际差异。
   - 区分基线中已有的改动、本次 AI 修改的文件，以及新生成但未跟踪的文件。
   - 测试或构建产生的临时文件也要检查，确认是否应删除或加入忽略规则；不得未经确认删除用户文件。

3. **向用户明确提醒**
   - 最终回复必须说明工作树中仍有哪些未提交改动，至少指出是否包含修改前已存在的改动。
   - 提醒用户及时检查、核对变更内容，并在确认后提交到 Git。
   - 当未提交文件较多时，明确提示不要让工作树长期保持大量未提交改动，建议按功能拆分并及时提交。
   - 若无法确定某些差异属于谁，直接标明“不确定”，不要把它归因给 AI。

4. **提交边界**
   - 未经用户明确要求，不执行 `git add`、`git commit`、`git reset`、`git clean` 或其他会改变提交边界的操作。
   - 用户要求提交时，也只能提交用户确认过的文件和差异；先再次展示范围，避免把既有无关改动混入提交。
   - 不为清理工作树而擅自丢弃任何未提交内容。

## 回复要求

源码修改完成后的收尾信息至少包含：

- 本次 AI 修改的文件和内容概述。
- 修改前已存在的未提交改动是否仍在。
- 当前工作树是否还有未提交改动。
- “请及时检查并核对上述差异，确认无误后提交到 Git；不要让工作树长期处于大量未提交改动的状态。”

此约定适用于所有会改变源码、测试、配置或构建相关文件的任务。
